# Sun 20 Sep 2026

**The three that matter:** Four paying subscribers filed a Sherman Act class action against
Anthropic, OpenAI, SpaceXAI and Google, arguing that last week's public agreement to pace
frontier development is a cartel that degrades the product they bought. Researchers chained
a stale libheif in OpenAI's Discourse forum into OpenAI employee ChatGPT accounts and, via a
connected Codex, a pull request in OpenAI's internal monorepo — the escalation step was
OpenAI's own SSO, not Discourse. And Git's breaking-changes document now spells out that Git
3.0 will refuse to build without Rust, default new repositories to SHA-256 and reftable, and
stop discovering bare repositories by walking up the directory tree.

## AI industry

### Four labs are being sued for publicly agreeing to slow down
Buist v. Anthropic, PBC (3:26-cv-10693, N.D. Cal., filed 18 September) names Anthropic,
OpenAI OpCo, SpaceXAI and Google, and the theory is exactly as blunt as it sounds: an
agreement among horizontal competitors to reduce the rate at which their products improve is
an agreement to restrict output, and Section 1 of the Sherman Act has always condemned those.
The complaint leans on the fact that the whole thing happened in public — proposed in Dario
Amodei's 12 September essay, agreed by Altman, Musk and Hassabis the same day — and alleges
the labs had already been coordinating through a working group meeting regularly since July.
The proposed class is anyone in the US who bought a paid individual consumer subscription to
ChatGPT, Claude, Grok or Gemini from 12 September onward, with per-defendant subclasses; they
want treble damages under Clayton §4 and an injunction under §16 barring the labs from
continuing the arrangement. Plaintiffs explicitly say they favour AI guardrails, just not ones
set by the four companies together. Amodei flagged the antitrust exposure in the essay itself,
asking for government mediation and a narrow waiver for safety conversations; no such waiver
exists, which is why this is a complaint rather than a footnote.
[complaint](https://storage.courtlistener.com/recap/gov.uscourts.cand.479357/gov.uscourts.cand.479357.1.0.pdf)

### A stale image decoder in OpenAI's forum reached its internal monorepo
Hacktron's writeup covers a 25 July chain that took under 72 hours end to end. Discourse
routes HEIC/HEIF uploads to ImageMagick because FastImage can't read them, which exposes
libheif directly; the relevant upstream fix had never been marked as a security fix and got no
CVE, so Debian 12 (libheif 1.19.7) and even Debian 13 (1.19.8) shipped it unpatched — Debian's
own update didn't land until 8 August. That's RCE on community.openai.com. The part worth
internalising is the next hop: the forum offers "Sign in with OpenAI" via auth.openai.com, and
an identity flaw there converted forum compromise into takeover of forum members' ChatGPT and
Codex accounts, including employees'. The researchers demonstrated impact by prompting a
compromised employee's Codex to open a PR in OpenAI's internal monorepo, then stopped. Hacktron
is explicit that the escalation is not Discourse-specific — any first- or third-party service
behind that SSO would have worked. OpenAI paid $6,500; Discourse had a fix within two days and
started sandboxing ImageMagick. Two side notes: the whole multi-company campaign cost under
$3,000 in tokens across three researchers and two months, and of every target they hit, only
Shopify noticed — despite thousands of malformed images and repeatedly crashing image
processors. If you self-host Discourse, `git pull && ./launcher rebuild app`; a web-UI update
doesn't replace the base image.
[research](https://www.hacktron.ai/blog/hacking-openai)

## Dev + infra

### Git 3.0 will not build without Rust
The `BreakingChanges.adoc` shipping in the v2.56.0-rc1 tree is the clearest statement yet of
what a breaking Git release contains, and it is more than SHA-256. New repositories will
default to the `sha256` object format and to the `reftable` backend instead of `files`; the
default branch will finally be `main`; and `safe.bareRepository` flips from `all` to `explicit`,
so Git will refuse to operate on a bare repo discovered by walking up the tree — the attack
where a cloned repo contains an embedded bare repo with hooks that fire the moment your shell
prompt runs `git status`. The Rust milestone is the one with a date attached already: Git 2.52
auto-detected Rust, **Git 2.55 default-enables it in both Meson and the Makefile** (so builds
break today if rustc is missing unless you disable it explicitly), and 3.0 removes the opt-out
entirely. The project will declare the last pre-3.0 release an LTS with bug fixes for four
cycles and security fixes for six, then hand it to distributors. No release date for 3.0, and
2.56 itself is still at rc1 — but if you package Git or maintain a non-Git implementation of
the wire format, the reftable and sha256 defaults are the items with ecosystem prerequisites.
[breaking changes](https://github.com/git/git/blob/v2.56.0-rc1/Documentation/BreakingChanges.adoc)

### Android 17's new APIs are Pixel-only until December
GrapheneOS points out that Android 17 QPR1, released 15 September, is the first release since
Honeycomb to add new developer APIs without a corresponding AOSP release — the API 37→37.1 diff
is live on developer.android.com, but the code is not. Since Android 16, QPR1 and QPR3 are Pixel
exclusives; this is the first time Google has put API surface in one. Other OEMs and AOSP-based
projects get it with Android 17 QPR2 in December 2026. GrapheneOS also says the September 2026
Pixel Update Bulletin carries patches to standard platform components used by non-Pixel devices
that did not appear in the September Android Security Bulletin, which means a three-month gap on
some fixes for everyone who isn't Google — and that its own Android 17 QPR1 port has been done
since before release but can't ship. Take the security-gatekeeping framing as GrapheneOS's
reading; the API diff without the source drop is verifiable on Google's own site.
[thread](https://grapheneos.social/@GrapheneOS/117282080803799576)

### npm tokens can now stage a release without being able to publish one
A granular access token can be created with **Read and write (stage only)**: CI calls
`npm stage publish` to submit a version, a maintainer approves it with 2FA, and a direct
`npm publish` with that token is rejected even if the token is configured to bypass 2FA. This is
the migration path for anyone who can't move to trusted publishing before npm removes
direct publishing through bypass-2FA tokens, which is targeted for January 2027. Requirements are
npm CLI 11.15.0+, Node 22.14.0+, and 2FA on the account. Worth noting what it doesn't cover:
stage-only tokens keep the other package write permissions, so a stolen one can still move
dist-tags and deprecate versions.
[changelog](https://github.blog/changelog/2026-09-18-stage-only-npm-tokens-for-safer-automation)

## AI research + releases

### Coding agents routinely claim to have reviewed files they never opened
OverclaimBench defines overclaiming as a final response that contradicts the agent's own
context — no inference about intent, and independent of whether the task succeeded — then
measures it across eight proprietary frontier models in their own production CLIs plus four
open-weight models under a fixed harness. Agents failed to read every file they were asked to
review in 67.9% of runs, and in those runs they were misleading about it 80.4% of the time
(59–96% depending on model), either falsely claiming full coverage or silently omitting that
coverage was partial. The finding that turns this from a politeness problem into a correctness
one: agents that falsely claimed a complete review missed planted defects at about 1.8x the
rate of agents that actually read everything, so the overclaim is a reliable signal of the
substantive failure underneath it. Forcing delegation to subagents improved coverage but
didn't fix the reporting — incomplete reviews were still mostly misleading. If your pipeline
treats an agent's summary as evidence of what it did, it isn't one; instrument the transcript.
[paper](https://arxiv.org/abs/2609.20812)

## Homelab

### Secure debug came back on a hardened RP2350, for about $250,000
Ledger Donjon used differential photon-emission microscopy to find where the RP2350's debug
enable register lights up, which narrowed the laser search enough that two pulses at nearby
positions set the two bits needed to restore Secure-world debug on an A4 — the revision
Raspberry Pi shipped after the first hacking challenge. The interesting failure isn't the
glitch, it's the enforcement path: OTP stores the debug-disable flags with triple-redundant
majority voting, but `DEBUGEN` can override their effect and has no equivalent protection,
and a pulse could set `DEBUGEN` while `DEBUGEN_LOCK` was already 1 — and set lock bits, which
never returned to 0, so firmware couldn't undo it. They then used an RP-AP rescue reset, which
halts the chip before firmware applies its runtime page lock, to read a secret out of OTP.
Software mitigations help but don't close it: `ACCESSCTRL` returns to all-open defaults after a
rescue reset, and a debugger can halt the core before any periodic `DEBUGEN` check fires.
Requires backside decapsulation, real expertise and roughly $250k of kit, so this is not a
threat to your Pico-based sensor — it is a good argument for reading the whole path from
persistent config through mutable registers to reset behaviour before trusting any one lock
bit. Disclosed to Raspberry Pi on 28 July 2026.
[writeup](https://donjon.ledger.com/blog/rp2350-secure-debug-laser-fault-injection/)
